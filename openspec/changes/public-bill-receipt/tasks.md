## 2. The Public Reader

- [x] 2.1 Write the failing tests first: the function returns a receipt for a valid token; returns the identical refusal for unknown, malformed, revoked and disabled; accepts no argument that widens it; and never returns customer name or phone.
- [x] 2.2 Add one `security definer` function taking **only** a token and returning one receipt: outlet, bill number, business date and time of sale, lines with quantity and snapshotted unit price, discount records with their basis, rounding, total, payment allocations, and the void state and reason. **It must not return `customer_name` or `customer_phone`** — the omission is enforced by the function's own projection, not by the page choosing not to render them. Returns `jsonb`, and it groups the discount rows itself rather than handing over raw lines — a menu discount is stored per line, and the row a person reads sums the lines carrying the same value, which is arithmetic the page must not be doing. **One deliberate departure from the design:** the receipt does not claim `All Items`. That is a claim about what the menu contained at the moment of sale, and this reader opens a bill months later with no menu history to check it against. #53's own manager bill detail declined it for exactly that reason (`categoryCount={Number.POSITIVE_INFINITY}`), so the receipt names the categories it actually carried rather than giving a second answer.
- [x] 2.3 Grant execute on that function to the service role only. **Add no policy and no grant for `anon` anywhere**, and add a test asserting an anonymous session is refused bills, bill items, payments, discounts and link rows even while holding a valid token. Not granted to `authenticated` either, which the design did not ask for and which follows anyway: a signed-in session reads bills through its own policies, and a `security definer` function that ignores those has no business being reachable from one.
- [x] 2.4 Add the kill switch as a flag the function itself honours, so disabling takes effect at the database for every caller with no deploy. Test that a disabled endpoint refuses identically rather than distinguishably.
- [x] 2.5 Add `bill_public_link_views` recording token, time, a non-reversible client address and user agent, written by the function **only when the token resolves**. A request that resolves to nothing must cause no write — a flood of invalid tokens must not become a flood of inserts (`design.md` §5, and the anti-amplification clause in the spec). The address is hashed **inside** the function, salted from `public_receipt_settings.viewer_salt`, so the raw value never reaches a column and the digest cannot be reproduced by anybody holding the Worker's source. An unsalted hash of an IPv4 address is walkable in seconds, so a bare digest would be the address. Asserted: the same address digests identically (or the record could not show a harvest at all) and differently from a bare SHA-256.
- [x] 2.6 **Isolation cases for `bill_public_link_views`**, same three roles, plus a case proving a view row cannot identify the customer. **Refused outright to all three roles, not merely scoped to their outlet** — stronger than the matrix's cross-outlet zero. Nothing in the app shows a franchise admin who opened a receipt, so no client role holds a privilege on the record and there is no outlet question to answer. The customer case is a column-list assertion, the same teeth `customer_lookup_attempts` gets in `01_schema_coverage.sql`: a catalog fact a later migration has to argue with rather than slip past.
- [x] 2.7 Regenerate schema types and commit the diff.
- [x] 2.8 SECTION GATE — one token in, one receipt out, no name, no phone, no second bill, no widening argument; four refusal cases indistinguishable; the switch works; invalid tokens write nothing.

## 4. What The Receipt Says

> The page and PDF are built in the companion repo (section 5). This section owns
> the **content contract** they implement, and is where #53's shape lands.

- [x] 4.1 Fix the receipt's field list against the post-#53 bill: lines at snapshotted list price, each discount as its own line naming its basis (`Menu Discount (15%)` over the categories it covered, `Discount (₹50)` over `On this bill`), the rounding line, the total. Held to the shape in `52_what_the_receipt_says.sql`, which rings each shared case as a real bill and reads the receipt back. The one departure from the design is recorded at 2.2: no `All Items` phrase, following the manager bill detail.
- [x] 4.2 Assert the receipt performs **no arithmetic**: every figure is a stored integer-paise column formatted at the display edge. Add a test over a discounted bill proving the rendered figures equal the stored ones, because a receipt that computes disagreeing with a bill that stored is the worst bug available here. **The grouping is summed twice and had to be held together.** A menu discount is stored per line, so the row a person reads is a sum — done by `groupMenuDiscounts()` for the counter's draft, which has no rows in the database, and by `bill_public_discount_rows()` in SQL for the receipt, which must do no arithmetic on the page. Neither can be the other, so `src/domain/discount-row-cases.json` is the one table both are held to, with `scripts/check-discount-row-cases.mjs` in `npm run lint` — the same shape `billing-totals-cases.json` already has for the bill identity. It earned its keep immediately: the two disagreed on category order. **Category order inside a row is deliberately not part of the shared rule** — the counter has its draft's line order and a settled bill has none, being listed by name — so both sides are compared with categories sorted, and everything that is a fact about money is compared exactly.
- [x] 4.3 Cover the ₹1 floor: a fully discounted bill renders the giveaway, the rounding that carried it to one rupee, and a ₹1 total, as honest figures rather than a rendering fault.
- [x] 4.4 Cover the void case (reads `Cancelled`, unmistakably) and the corrected-tender case (reads the corrected split), both from a live read. **The void case found a real bug and the corrected case found a worse one.** The reader was projecting `bill_payments` directly, which is the pre-correction split: a correction is an append, a new revision with its own allocations, so the original rows survive and reading them would have served a customer the allocation that was corrected away. It reads `effective_bill_payments` now, as the manager's own bill detail does.
- [x] 4.5 Confirm no tax line, no GSTIN, and nothing resembling a tax invoice while every bill is `no_tax`. Asserted across **every** shared case rather than one, and on four spellings (`gstin`, `invoice`, `hsn`, `cgst`) plus a zero `tax_paise`, because the risk is a field nobody thought to check.
